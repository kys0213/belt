# 가짜 환경 E2E 테스트

> **Plan — 이 시점의 결정 기록.** 현재 정책의 신뢰 소스가 아니다.
> 날짜: 2026-10-11 · 브랜치: epic/notification-hitl-impl · PR: #882 · 승인 출처: 사용자 승인 (범위·진행 방식 확인 질문에 "이대로 자율주행")

## 배경

- PR #882 는 SQLite 단일 상태 기준, HITL first-wins, 실행 중 취소, GitHub 알림 channel 을 구현했다. 단위·통합 테스트는 green 이지만 빌드한 `belt` 바이너리를 daemon·CLI 로 끝까지 돌려 본 적은 없다.
- 기존 `e2e_real.rs` 는 `kys0213/belt` 에 실제 이슈를 만든다. 사용자는 외부 호출 없는 로컬 가짜 환경만 쓰기로 했다.

## 결정

- 빌드한 `belt` 바이너리를 subprocess 로 띄운다. 외부 의존은 `PATH` 앞에 둔 가짜 `gh` 와 가짜 runtime 으로 바꾼다. 가짜 `gh` 는 이슈·코멘트·라벨 상태를 파일에 둔다.
  - 버린 안: 실제 GitHub 전용 repo. 사용자가 외부 호출을 원하지 않았다.
  - 버린 안: 라이브러리 수준 통합 테스트만 추가. 바이너리 조립(설정 로드·IPC·프로세스 그룹)이 검증되지 않는다.
- 테스트는 `crates/belt-cli/tests/` 아래 E2E 전용 파일로 두어 단위 테스트와 분리한다.
- 시나리오:
  1. 수집 → 실행 → Done → worktree 정리
  2. 실패 → escalation retry → 파생 아이템과 work_id 연결
  3. HITL 열림 → 라벨 → 코멘트 `/belt done` 응답 → 늦은 CLI 응답은 already_handled
  4. 실행 중 `belt queue skip` 취소 → 프로세스 종료 → Skipped/canceled
  5. daemon 부재 시 CLI 직접 취소 → canceled_directly
  6. v1 DB 로 시작 → v2 마이그레이션 → `.bak-v1`
  7. Failed 아이템이 남아 있으면 재수집하지 않음
- 시나리오별 기대 결과는 QA 관점 agent 가 spec 위치를 근거로 정하고, 테스트 작성은 다른 agent 가 맡는다.
- E2E 가 결함을 찾으면 재현 테스트를 먼저 두고 고친다. 결과는 epic 브랜치에 커밋해 PR #882 에 포함한다.
